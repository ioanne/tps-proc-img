Trabajo Práctico N.º 1 · Procesamiento de imágenes

Editor de imágenes con Pillow y OpenCV

Implementar, con programación orientada a objetos, el núcleo de un servicio web que recibe imágenes, les aplica diez ediciones y guarda los resultados.

Modalidad: en equipos Stack: Python · FastAPI · SQLAlchemy · Pillow · OpenCV Entrega: 24/09/2026

1Objetivo

Se entrega una aplicación web con el frontend terminado y un backend con toda la API armada: endpoints, modelo ORM, consultas a la base, manejo de archivos en disco, excepciones de dominio y el servicio que coordina cada caso de uso. Lo que falta es el procesamiento de imágenes: abrir, validar y codificar imágenes con Pillow, y las diez operaciones de edición con Pillow y OpenCV. Mientras no estén, esas partes responden 501 Not Implemented. El trabajo de cada equipo es escribir esas clases.

Al terminar, el frontend tiene que funcionar de punta a punta sin haber tocado una sola línea de su código: subir una imagen, verla en la galería, aplicarle cualquiera de las diez ediciones, encadenar ediciones sobre el resultado, descargarla y eliminarla.

Los objetivos de aprendizaje son:

  • Manipular imágenes con Pillow y OpenCV, y entender la representación de cada librería (objetos PIL.Image vs. arreglos numpy en BGR).
  • Diseñar una solución orientada a objetos: abstracción, herencia, polimorfismo, encapsulamiento y separación de responsabilidades.
  • Construir una API REST con FastAPI respetando un contrato ya definido.
  • Persistir metadatos en una base de datos, guardando los archivos en disco y registrando su URL (no el binario) en la tabla.
  • Escribir tests automatizados.

3Arquitectura

La aplicación se organiza en capas. Cada capa solo conoce a la de abajo.

Regla de oro

Cada cosa vive en un solo lugar:

  • Las consultas SQL van en app/dal.py y en ningún otro archivo.
  • El manejo de archivos va 100 % en el core: leer el upload a memoria, guardar los bytes en disco con un nombre único, armar la URL que se registra en la base, leer y borrar (core/storage.py).
  • El procesamiento de imágenes (Pillow / OpenCV) va en el core: core/imaging.py y core/operations.py. Ni el servicio, ni el almacenamiento, ni el DAL saben qué es un píxel.
  • Los endpoints solo reciben el request, le piden el trabajo al servicio y devuelven el resultado. No procesan imágenes, no tocan archivos y no consultan la base.

El core no importa nada de FastAPI y tiene que poder usarse desde un script o un test sin levantar el servidor.

4Requisitos funcionales

RF1 · Subir imagen POST /api/imagenes

Ya viene implementado (ImageCodec.inspect + ImageService.upload). Se describe para que sepan cómo se comporta.

  • Recibe el archivo como multipart/form-data en el campo archivo.
  • Acepta PNG, JPEG, WEBP y BMP (config.FORMATOS_PERMITIDOS). El formato se determina por el contenido del archivo, abriéndolo con Pillow, y no por la extensión ni por el content-type. Un PNG llamado foto.jpg es un PNG.
  • Las validaciones se hacen en este orden, y la primera que falla define la respuesta:
    1. Supera config.TAMANIO_MAXIMO_BYTES (10 MB) → 413 ARCHIVO_DEMASIADO_GRANDE.
    2. No se puede abrir como imagen (corrupto, vacío, texto…) → 400 ARCHIVO_INVALIDO.
    3. Es una imagen válida pero de otro formato (GIF, TIFF…) → 400 FORMATO_NO_SOPORTADO.
  • El archivo se guarda tal cual se recibió en config.STORAGE_DIR, con un nombre único generado por el backend (por ejemplo un UUID) y la extensión que corresponde a su formato. Nunca se usa el nombre que mandó el usuario como nombre de archivo.
  • Se registra en la base de datos su URL pública (/media/<nombre_archivo>) y sus metadatos. tamanio_bytes es el tamaño del archivo guardado. Responde 201 con un ImagenOut.

RF2 · Listar imágenes GET /api/imagenes

Devuelve todas las imágenes, originales y resultados, ordenadas por id descendente (la más nueva primero). Si no hay ninguna, devuelve [].

RF3 · Obtener una imagen GET /api/imagenes/{id}

Devuelve el ImagenOut de esa imagen, o 404 (IMAGEN_NO_ENCONTRADA) si no existe.

RF4 · Eliminar una imagen DELETE /api/imagenes/{id}

  • Borra el registro y el archivo del disco. Responde 204 sin cuerpo, o 404 si no existe.
  • Las imágenes derivadas de la eliminada no se borran: su origen_id pasa a null.

RF5 · Aplicar una edición POST /api/imagenes/{id}/{operacion}

  • Aplica la operación sobre la imagen {id} con los parámetros del cuerpo JSON.
  • La imagen de origen nunca se modifica, ni su archivo ni su registro. El resultado es una imagen nueva, con su propio archivo y su propio registro, donde:
    • origen_id es el id de la imagen de origen;
    • operacion es el nombre de la ruta (brillo, escala-grises…);
    • parametros es el cuerpo con los valores por defecto ya aplicados, es decir params.model_dump(). Por ejemplo, {"ancho": 50} se guarda como {"ancho": 50, "alto": null, "mantener_proporcion": true}. En escala-grises es {};
    • nombre_original se hereda del origen.
  • El resultado se guarda en el mismo formato de archivo que el origen (un JPEG da un JPEG). Si el modo de color no se puede guardar en ese formato (por ejemplo RGBA en JPEG), se convierte antes de guardar.
  • Responde 201 con el ImagenOut del resultado. Si los parámetros violan una regla de dominio responde 400 (PARAMETROS_INVALIDOS); si la imagen no existe, 404 (IMAGEN_NO_ENCONTRADA). Los parámetros se validan antes de buscar la imagen, así que si fallan las dos cosas, gana el 400.
  • Se puede aplicar una edición sobre un resultado (el frontend lo permite con el botón “Seguir editando desde el resultado”).

Modos de color

Todas las operaciones tienen que funcionar con cualquier imagen aceptada, sea cual sea su modo de color:

  • Las imágenes en modo L (grises), RGB y RGBA se procesan en su modo.
  • Cualquier otro modo (P con paleta, LA, CMYK…) se convierte antes de procesar: a RGBA si tiene transparencia y a RGB si no.
  • En una imagen RGBA, las operaciones de color (brillo, contraste, saturación, nitidez) no modifican el canal alfa.
  • escala-grises y bordes siempre devuelven una imagen L, de un solo canal y sin alfa.

5Las 10 operaciones

Los rangos de la tabla ya los valida FastAPI con los schemas de schemas.py (si no se cumplen, responde 422 automáticamente). La columna Comportamiento esperado es lo que verifican los tests de aceptación. Lo marcado como regla es una validación que tiene que hacer el core y que se responde con 400.

La columna Sugerencia es orientativa: cada equipo elige si usa Pillow u OpenCV en cada caso, pero el trabajo tiene que usar las dos librerías en al menos dos operaciones cada una.

7Diseño con clases

La infraestructura ya está resuelta: ImageService, FileStorage, ImageDAL, las excepciones de dominio (core/exceptions.py), su traducción a HTTP (errors.py) y la subida de imágenes. El servicio define el contrato que tiene que cumplir el procesamiento:

  • ImageCodec.inspect(content) → ImageInfo (dado): abre los bytes, devuelve formato (detectado por contenido), ancho y alto. Si no es una imagen lanza InvalidFile. No filtra formatos: eso lo hace el servicio con config.ALLOWED_FORMATS.
  • ImageCodec.open(content) → Image: abre un archivo guardado, listo para procesar (normalizando el modo de color).
  • ImageCodec.encode(image, format) → bytes: codifica el resultado en memoria en el formato del origen, convirtiendo el modo si hace falta. El servicio después le pasa esos bytes al almacenamiento.
  • Operation (en core/operations.py): clase abstracta con name, parameters y apply(image) → Image. Los routers ya construyen cada subclase con los campos de su schema.

Dentro de ese contrato, cada equipo diseña su solución; no hay una única correcta. Estos son los requisitos mínimos:

  1. Una subclase de Operation por operación (diez en total, ya declaradas con su constructor). Cada una recibe sus parámetros en el constructor y los valida ahí, lanzando InvalidParameters: no tiene que poder existir un objeto Blur con kernel par. Pueden agregar clases intermedias a la jerarquía (por ejemplo, una base para las operaciones de ImageEnhance).
  2. Polimorfismo en lugar de condicionales. Ninguna parte del código puede tener un if/elif que decida qué hacer según el nombre de la operación. El código que aplica una operación tiene que funcionar con cualquier subclase sin cambios, y agregar una operación número 11 no debería requerir modificar las clases existentes.
  3. Usar las excepciones de dominio dadas (InvalidParameters, InvalidFile…). El exception handler ya las traduce a HTTP; no agreguen try/except en los endpoints.
  4. Conversión Pillow ↔ OpenCV encapsulada. Pillow trabaja en RGB y OpenCV en BGR. Esa conversión tiene que vivir en un único lugar reutilizable, no copiada en cada operación.
  5. El core no depende de FastAPI. Ningún archivo de app/core/ puede importar fastapi.
  6. Usar type hints en todas las firmas públicas y respetar PEP 8.

Cómo queda un endpoint

Los routers ya están escritos así:

@router.post("/blur", summary="6. Blur", **OPTIONS)
def apply_blur(image_id: int, params: BlurIn, service: ImageService = Depends(get_image_service)):
    return service.apply(image_id, Blur(**params.model_dump()))

Toda la lógica está en el core. Como la operación se construye antes de llamar al servicio, si Blur lanza InvalidParameters el exception handler responde 400 sin llegar a buscar la imagen.

La persistencia viene resuelta. app/models.py define el modelo ImageRecord (tabla images) y app/dal.py concentra todas las consultas en ImageDAL: create, get, list, update y delete. Las columnas son:

La tabla guarda la URL y los metadatos; el binario queda en storage/images/. FastAPI ya sirve esa carpeta en /media, así que el frontend puede mostrar la imagen directamente desde la URL.

El archivo lo guarda FileStorage.save, que devuelve un StoredFile con file_name, url y size_bytes: justo lo que el servicio registra con el DAL. database.py activa las claves foráneas de SQLite, así que el ON DELETE SET NULL de source_id funciona.

Usen siempre app.config

La carpeta de imágenes (STORAGE_DIR), la URL de la base (DATABASE_URL), los formatos y el tamaño máximo se toman siempre de app/config.py, nunca escritos a mano en el código. Los tests de aceptación redirigen la carpeta y la base a un directorio temporal con las variables de entorno TP_STORAGE_DIR y TP_DATABASE_URL, y si el core usa otras rutas, los tests fallan.

tests/test_contract.py es este enunciado escrito como código. Usa la API igual que el frontend y verifica cada regla de las secciones 4, 5 y 6: códigos HTTP, formato de errores, orden del listado, que el archivo quede en STORAGE_DIR y la URL en la tabla images, que el origen no cambie, píxeles concretos de cada operación, formatos y modos de color.

Arrancan 121 failed, 32 passed. Todos tienen que pasar y no se pueden modificar. Si alguno parece contradecir el enunciado, consúltenlo en el foro en vez de cambiarlo.

Tests propios del equipo

Además, en archivos nuevos dentro de backend/tests/:

  • Tests unitarios del core: al menos uno por operación, sobre imágenes creadas en memoria (por ejemplo, Image.new("RGB", (40, 20), "red")), sin tocar disco ni base de datos. Comprueben propiedades concretas: que el espejo horizontal invierta el píxel de la esquina, que la redimensión con proporción dé el alto esperado, que la escala de grises tenga un solo canal, etc.
  • Tests de validación: que construir una operación con parámetros inválidos lance la excepción de dominio correspondiente.
  • Tests del codec: que encode pueda guardar una imagen RGBA como JPEG y que open devuelva una imagen en un modo que las operaciones puedan procesar.

Los tests propios prueban las clases del core directamente. Los de aceptación prueban la API desde afuera: se complementan, no se reemplazan.

10Entrega

  • Un repositorio Git por equipo con el historial de commits de todos los integrantes. No se aceptan entregas en un único commit.
  • Un README.md en la raíz con:
    • integrantes del equipo,
    • instrucciones para instalar, correr la app y correr los tests,
    • el diagrama de clases del core (imagen o Mermaid),

Restricciones

  • No se modifica nada de frontend/, app/schemas.py, app/config.py, tests/conftest.py ni tests/test_contract.py. Si la solución necesita cambiarlos, está violando el contrato.
  • Se pueden agregar archivos y dependencias (hay que declararlas en requirements.txt).
  • Pillow y OpenCV no se reemplazan por otras librerías de procesamiento de imágenes.

Sugerencia de orden de trabajo

  1. Leer core/service.py para entender qué espera el servicio del codec y de las operaciones.
  2. ImageCodec.open y ImageCodec.encode, y las operaciones más simples (espejo, escala de grises, brillo). Verificar desde el frontend. Con eso pasan también test_list_includes_derived y test_derived_images_are_kept_without_source.
  3. El resto de las operaciones, con sus tests.
  4. Tests de integración, README y diagrama.

Una forma práctica de repartirse el trabajo es que, una vez definida la clase base, cada integrante tome algunas operaciones.

11Uso de IA

Pueden usar IA, pero como herramienta para aprender, no para resolver el TP. El trabajo existe para que aprendan a diseñar con clases y a procesar imágenes, y si la IA escribe el código ese aprendizaje no ocurre. La fuente principal son los apuntes de la materia y la documentación de Pillow y OpenCV. La IA viene después, para destrabarse o para contrastar lo que ya pensaron.

Para qué sí

  • Discutir la arquitectura del core. Pueden pedirle que proponga cómo organizar la jerarquía de Operation para que el core sea reutilizable: dónde validar, qué clases intermedias conviene tener, dónde encapsular la conversión Pillow ↔ OpenCV, cómo agregar una operación nueva sin tocar las existentes. Tómenlo como una propuesta para discutir en equipo y comparar con lo visto en clase, no como la solución. Quédense solo con lo que puedan justificar.
  • Hacer preguntas concretas. Por ejemplo: ¿qué diferencia hay entre cv2.blur y cv2.GaussianBlur? ¿Por qué JPEG no puede guardar una imagen RGBA? ¿Cómo paso una imagen de Pillow a un array de numpy y de vuelta?
  • Entender un error que no pudieron resolver solos, después de haberlo intentado y de haber leído el traceback.
  • Revisar código que ya escribieron: pedir una crítica del diseño o de la legibilidad, no que lo reescriba.

Para qué no

  • Pegar el enunciado y pedir el TP resuelto.
  • Pedirle que haga pasar los tests de aceptación.
  • Copiar código que no pueden explicar línea por línea.

Cómo preguntar

Nunca tiren un prompt sin sentido ni sin un objetivo claro. Antes de escribir, tengan claro qué quieren saber y cómo van a darse cuenta de si la respuesta sirve. Un buen prompt da contexto (qué están haciendo y qué ya saben), hace una pregunta puntual y dice qué tipo de respuesta esperan.

13Extras (opcionales)

Suman puntos solo si todo lo obligatorio está completo. Van en endpoints nuevos, sin romper el contrato existente:

  • Pipeline: POST /api/imagenes/{id}/pipeline recibe una lista de operaciones con sus parámetros y las aplica en orden, guardando solo el resultado final. Pista: patrón Composite.
  • Historial: GET /api/imagenes/{id}/historial devuelve la cadena de imágenes desde la original hasta {id}.
  • Operaciones nuevas: sepia, negativo, binarización (Otsu), ecualización de histograma. Si el diseño es bueno, agregarlas no requiere tocar las clases existentes.
  • Miniaturas: generar y servir una versión reducida de cada imagen para la galería.

14Preguntas frecuentes

¿Puedo cambiar las firmas de los endpoints?

Pueden cambiar los parámetros internos (por ejemplo, agregar dependencias con Depends), pero no la ruta, el método, el cuerpo ni la respuesta.

¿Tengo que usar las dos librerías en todas las operaciones?

No. Cada operación usa la que el equipo prefiera, pero en el total del trabajo cada librería tiene que aparecer en al menos dos operaciones.

El frontend dice “Servidor desconectado”.

El backend no está corriendo. Abran el frontend desde el propio backend (http://localhost:8765). Si lo sirven con otra herramienta o el backend usa otro puerto, indiquen dónde está la API agregando ?api=http://localhost:PUERTO a la URL.

Al aplicar una edición dice “La imagen no está en el servidor”.

Esto pasa cuando la subida falló (por ejemplo, un formato no soportado o un archivo de más de 10 MB) y el frontend solo muestra una vista local. Revisen el error en el panel Actividad.

¿Qué pasa si roto una imagen JPEG con expandir?

Aparecen esquinas nuevas y se rellenan de negro (en RGBA, transparentes). Ojo: si el core convierte a RGBA para rotar, tiene que volver a un modo que JPEG pueda guardar.

Mis tests pasan en mi máquina pero no los de aceptación, por las rutas.

Seguramente usan una ruta escrita a mano en lugar de config.STORAGE_DIR o config.DATABASE_URL. Ver la sección 8.

¿Puedo usar OpenCV para leer y escribir los archivos?

Sí, siempre que el resultado cumpla el contrato (formato, modo y tamaño). Lo más simple es leer y escribir con Pillow y convertir a numpy solo para las operaciones de OpenCV.
